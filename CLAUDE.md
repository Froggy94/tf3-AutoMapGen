# CLAUDE.md

## Purpose

tf3-AutoMapGen (tf3-Auto-map-generator-framework) generates realistic Transport Fever 3 maps from real geodata
(elevation models, ESA WorldCover, OpenStreetMap): heightmaps, landcover masks, towns, industries, roads and a matching
climate mod. It is open source (Apache-2.0) and meant to become a standard tool for TF3 map making, so architecture
and code quality are requirements, not extras.

A private predecessor (the "legacy project") is the **functional template**: its algorithms were taken over as nodes
(logic, not structure) and its results are the reference of the comparison tests (skipped when it is not present).

## Conventions

- Everything in this repository is English: code, comments, docs, commit messages, GUI texts (translations later via
  a text catalog). In-game texts are bilingual (DE + EN).
- Report clearly what is verified (tests, game) and what is untested.

## Architecture in one paragraph

A declarative, typed dataflow graph with plugin nodes. Five concerns, each changing for its own reason:
**data** (immutable typed values), **parameters** (pydantic schemas in code, values in TOML parameter sets),
**processing** (nodes = small pure functions, stable contract), **composition** (JSON graph documents, layered by
`extends`, editable by a future graph editor), **execution** (engine: checks, order, lineage cache, memory, previews).
New behaviour = new wiring or parameters; code only for a new node or data type. Code map: `docsAI/code_map.md`,
decisions: `docsAI/adr/`.

## Code requirements

1. **Nodes are pure functions** (`@node`): no file/env/global access, no mutation of inputs; I/O only in nodes
   declared `side_effects=True` and in source nodes; randomness only from a seed parameter.
2. **Everything else is strictly object-oriented:** single responsibility, dependencies injected via the constructor,
   extension via registries/strategies, no module-level code except definitions and constants, no global mutable
   state.
3. **Separation of data, parameters and logic** as above; I/O only at the edges.
4. `automapgen.graph` knows no domain; node packages use only its public API (`automapgen.graph`). Checked by
   `tests/unit/test_architecture.py`.
5. Clean-code criteria (priority): readability, SRP, low coupling, testability (very high); KISS, naming, cohesion,
   traceable errors (high); DRY, small units, consistent style (medium); comments where they help.
6. `mypy --strict`, ruff and tests are green before every commit.

## Documentation

Two separate trees with different readers and rules. A fact lives in exactly one place; other files link to it.

**`docsAI/` - for AI assistants and maintainers.** Terse bullets, no prose; stable anchors (paths, node ids, class
names); every game fact with status (verified / *unverified*), source (file, node, log, test) and absolute date; link
instead of repeating.

| File | Content |
|---|---|
| `docsAI/code_map.md` | package -> responsibility |
| `docsAI/glossary.md` | terms (game metre, reference height, real/painted water, draft/final ...) |
| `docsAI/reference/` | for AI assistants of map makers: README (how to change presets, projects, graphs) + `nodes.md`, `graphs.md` generated by `automapgen reference` (a test checks they are current) |
| `docsAI/adr/NNNN-*.md` | architecture decisions: context, decision, alternatives, consequences |
| `docsAI/notes/*.md` | verified knowledge: `tf3_facts.md` (the game), `legacy_differences.md`, `numpy_and_files.md` |

**`docsHuman/` + `README.md` - for people** (map makers, developers, reviewers). Clear, precise language; the why
first; short explanations with examples and diagrams; internal ids only where needed; no working notes; facts are
linked to `docsAI/notes/` or stated with their source.

| File | Content |
|---|---|
| `README.md` | entry: goal, approach, status, limits, quick start |
| `CHANGELOG.md` | changes per version |
| `docsHuman/climate_mod.md` | the game's terrain generator, import layers, what the climate mod does |
| `docsHuman/getting_started.md` | for map makers: install the Windows build, first map, into the game, changing things with an AI assistant |
| `docsHuman/example.md` | the Brenner map step by step |
| `docsHuman/architecture.md` | principles, what a graph is, how the classes work together |
| `docsHuman/node_guide.md` | writing nodes; graph documents, parameter sets, compilation, execution |
| `docsHuman/graphs/*.md` | built-in graphs as Mermaid (generated: `automapgen show <id>`) |

**After a code change:** new findings to `docsAI/notes/`; decisions as ADR; `automapgen reference` after a change of
nodes or graphs; `docsHuman/` only where people would see a difference.

## Commands

```
.venv/Scripts/python.exe -m pytest            unit tests (slow comparison tests: -m slow)
.venv/Scripts/python.exe -m mypy               strict type check
.venv/Scripts/python.exe -m ruff check src tests
.venv/Scripts/automapgen.exe nodes | check GRAPH | show GRAPH | run GRAPH --set FILE --name NAME | schema | reference
.venv/Scripts/python.exe packaging/build.py      Windows build (needs the extra `build`): dist/tf3-AutoMapGen-<version>-windows.zip
Comparison tests need the legacy project next to this one and network (WorldCover).
```
